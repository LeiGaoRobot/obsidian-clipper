# AI Redesign Phase 5: Settings AI section

Spec: [[2026-10-19-ai-subsystem-redesign-design]]. Previous: [[2026-10-22-ai-redesign-phase-4-job-runner]]. Branch: `ai-redesign`.

**Goal:** Persist the v2 AI settings (per-key sync layout, D1) with a per-device, idempotent migration from v1; move API keys to non-synced `storage.local`; replace the Interpreter settings section with one **AI** section that is the only code path writing AI settings; add browser gating, an explicit **Test** per connection (D3) with a persisted status, and a redacted Diagnostics log. The user's existing configuration must survive, and no v1 key is deleted.

This phase ships as three sub-phases. Each leaves the extension fully working, with green tests, type check, three builds, and bundle checks:

- **5a — v2 storage foundation.** Codec, defaults, pure migration with fixtures, the catalog, the settings store, and a v2 loader that every reader (gateway, popup, Reader runtime) uses. The loader still derives from v1 when no v2 keys exist, and persistence is off, so behavior does not change.
- **5b — AI section and sole writer.** The new section, the persisted migration switched on, every v1 writer retargeted or deleted, the old Interpreter UI, readiness assistant, upstream catalog fetch, and DeepSeek override removed.
- **5c — Test, status, Diagnostics.** Listing and probe adapters, the `test` Port message, persisted connection status, `structuredOutput` folded into the connection, the Diagnostics ring buffer, Safari one-shot Test.

## Constraints

- **Nothing destructive to v1.** `interpreter_settings` and `reader_settings.learningResponseLanguage` stay in sync storage untouched; the new build only stops writing `interpreter_settings`. Deleting v1 keys is a later release (spec, Migration).
- **Background-only network, static imports.** `settings.ts`, `migrate.ts`, `catalog.ts`, `diagnostics.ts`, and the listing adapter are DOM-free, take storage areas by injection, and are statically imported into `background.ts`. `npm run test:bundle-boundaries` stays green. The Settings UI stays a lazy chunk.
- **No credentials in messages or the page DOM.** The `test` message carries a connection id; the gateway resolves the credential from `ai_credentials`. Test results never echo a key.
- **User actions only.** Test runs on an explicit click. Loading Settings, opening the popup, or changing a selection never sends a model request. Credential bootstrap and the sync migration are storage work only.
- **Sync quota.** `chrome.storage.sync` allows 8,192 bytes per item and 102,400 bytes in total. Every write is checked before it is sent, and a quota failure is a visible Settings error, never an unhandled rejection.
- **Connection kinds stay as implemented** (`src/ai/types.ts`): Gemini, OpenRouter, DeepSeek, xAI, and Meta are `openai-compatible` with a `presetId`. The spec's separate `openai` / `gemini` / `openrouter` kinds are not needed for listing or routing.
- **Plaintext.** `storage.local` is plaintext on disk. The docs say that moving keys there stops them syncing and relieves the quota, and that it is not encryption.

## Decisions made here

1. **Storage keys and shapes.** Every object carries `v: 1` so a later layout change can be detected per key.

   | Area | Key | Shape |
   | --- | --- | --- |
   | sync | `ai_connections` | `{ v: 1, items: Connection[] }` |
   | sync | `ai_profiles` | `{ v: 1, items: ModelProfile[] }` |
   | sync | `ai_routing` | `{ v: 1, defaultProfileId?, taskProfiles: Partial<Record<AiTask, string>>, responseLanguage? }` |
   | sync | `ai_interpreter` | `{ v: 1, enabled: boolean, autoRun: boolean }` |
   | sync | `ai_prompt_context` | `{ v: 1, text: string }` |
   | local | `ai_credentials` | `{ [connectionId]: string }` (spec shape; versioned by `ai_migration`) |
   | local | `ai_migration` | decision 4 |
   | local | `ai_connection_status` | `{ [connectionId]: ConnectionStatus }` (decision 10) |
   | session | `ai_diagnostics` | `{ v: 1, entries: AiDiagnosticEntry[] }` (decision 12) |

   `Connection` gains nothing; `structuredOutput` (already typed) is now persisted. `AI_SETTINGS_DEFAULTS` in `src/ai/settings.ts` is the one place for defaults: `enabled: false`, `autoRun: false`, `defaultPromptContext: ''`, `taskProfiles: {}`, no `responseLanguage`. `decodeAiSettings(sync, local, nativeMessaging)` sanitizes each key independently (drops items without a string id or with an unknown `kind`, drops duplicate ids keeping the first, coerces booleans, normalizes Codex `model` / `options.reasoningEffort` with the existing normalizers, trims `responseLanguage`) and returns an `AiSettingsView`. A key that fails to decode falls back to its default without touching the others, so one corrupt item cannot blank the whole configuration.
2. **Store, not module globals.** `createAiSettingsStore({ sync, local, session?, onChanged?, nativeMessaging, bootstrap })` in `src/ai/settings.ts` returns `{ load, saveConnections, saveProfiles, saveRouting, saveInterpreter, savePromptContext, setCredential, deleteCredential, observe }`. Areas are `StorageAreaLike` (from `job-store.ts`) plus `remove`. `load()` reads the six keys in two `get` calls, runs the bootstrap (decision 4) when `bootstrap` is true, and returns the decoded view. Each `saveX` writes exactly one sync key after `assertSyncItemSize` (JSON byte length ≤ 8,192) and maps a thrown `QUOTA_BYTES*` / `MAX_WRITE_OPERATIONS*` runtime error to `AiSettingsStorageError` with `reason: 'item-too-large' | 'total-quota' | 'write-rate'`. `observe(listener)` filters `storage.onChanged` to the AI keys across the three areas and reports which keys changed. `src/utils/ai-settings.ts` wires the browser areas for UI contexts (`loadAiSettings()`, `aiSettingsStore`); `background.ts` wires its own instance. The gateway's `deps.loadSettings` becomes `loadAiSettings: () => Promise<AiSettingsView>`, and `deriveAiSettings` is no longer called from the gateway.
3. **Derived mode until the switch.** When no `ai_connections` key exists and `bootstrap` is false, `load()` returns `deriveAiSettings(v1)` exactly as today. `AI_V2_BOOTSTRAP` in `settings.ts` is `false` in 5a and flipped to `true` in the 5b switch commit, so every reader can move to the loader first with no behavior change.
4. **Migration** (`src/ai/migrate.ts`, pure). `migrateV1(raw: { interpreter_settings?, reader_settings? }): { sync: V2SyncBundle; credentials: Record<string, string> }` sanitizes the raw v1 item the way `loadSettings` does (string ids only, mode coerced to `api` unless `grok` / `codex`, Codex fields normalized) and reuses `deriveAiSettings`, then:
   - keeps only the CLI connection and profile of the active mode (API mode: none). Users add a CLI later through **Add local CLI**. Ids are deterministic: connection id = v1 provider id, profile id = v1 model id, CLI ids are the existing `legacy-cli-*` constants;
   - sets `presetId` when the v1 `baseUrl` equals a catalog entry's `baseUrl` (v1 never set it), then `kind` from `inferConnectionKind` as today (preset, host, legacy name);
   - copies `readerSettings.learningResponseLanguage` (trimmed) to `routing.responseLanguage`;
   - returns the non-empty `apiKey`s keyed by connection id, never placing them in the sync bundle.

   **Bootstrap** in `load()`: if `ai_connections` is absent, compute the bundle from the raw v1 items read in the same `get`, write the five sync keys in one `set`, write `ai_credentials` and `ai_migration` in one local `set`. If `ai_connections` is present, reuse it and write nothing to sync. Then **credential bootstrap** runs on every device on every load while a v1 key still exists: for each v2 connection whose id has a non-empty v1 `apiKey`, no local credential, and no entry in `ai_migration.credentials`, import the key and append the id. The record:

   ```ts
   interface AiMigrationRecord {
     v: 1; status: 'bootstrapped' | 'reused'; at: number; build: string;   // manifest version
     source: { providers: number; models: number; mode: 'api' | 'grok' | 'codex' };
     credentials: string[];   // connection ids whose v1 key was imported on this device, ever
   }
   ```

   The `credentials` list is what keeps a key the user deleted in the new Settings from being re-imported on the next load. **Old build after migration:** v2 is the source of truth once present; v1 changes made by an older build are ignored except through the credential rule above. **Two devices:** both compute the same bundle from the same v1 (no timestamps or randomness in the bundle), so concurrent first runs converge; a provider added on an old build during the sync-lag window of a concurrent first run is not carried over and must be re-added (documented, not merged, because an additive merge would resurrect connections deleted on the new build). Fixtures cover every legacy shape (empty, API-only, providers without `apiKeyRequired`, models whose provider is missing, Grok mode, Codex mode with and without model and effort, stale `interpreterModel`, missing `reader_settings`), the interleavings (A bootstraps then B reuses and imports its key; A and B both bootstrap; B's deleted credential is not re-imported), and an old build rewriting v1 after migration (no change to v2, new v1 key imported only where allowed).
5. **Sole writer means one v2 store.** After 5b no code writes v1 AI settings: `saveSettings` drops `interpreter_settings` from its `set` call (`loadSettings` still reads it for the `Settings` type until Phase 7), `interpreter-settings.ts`, `language-learning-readiness.ts`, `provider-presets.ts`, their tests, and `drag-and-drop.ts`'s `handleModelReorder` are deleted, and the three remaining user-facing writers go through the store:
   - **Popup model select** (`interpreter.ts`, `popup.ts`): lists every enabled profile in `<optgroup>`s per connection, CLI profiles included, so it is always visible. Its initial value is `resolveProfile(view, 'interpret')`. A change writes `routing.taskProfiles.interpret`, or deletes that entry when the choice equals `defaultProfileId`, so the routing table reads "Default" unless the user diverged. The stale-model self-heal is gone; the resolver reports `not-configured` instead. `handleInterpreterUI` takes `profileId` instead of `ModelConfig`.
   - **Reader engine switch** (`transcript-language-learning.ts`, runtime): the error card's select lists enabled profiles (label `connection · model`), and **Switch and retry** writes `routing.taskProfiles[task]` for the task that failed (`translate`, `reading`, or `explain`; the runtime puts `task` in the error details) and retries. The `tools` interface replaces `getExecutionInfo()` / `setExecutionMode(mode)` with `getExecutionInfo(task)` (resolved profile label, kind, and `TRANSCRIPT_GROUP_BUDGETS[kind][task]`), `listProfiles()`, and `setTaskProfile(task, profileId)`. Profile is not part of the job id, so checkpoints are reused across the switch as before.
   - **Response language** moves from the Reader section to the AI section's Language panel and writes `routing.responseLanguage`. `reader.ts` reads `ai_routing` next to `reader_settings` to pass `responseLanguage` to the transcript UI; `language-learning-vocabulary.ts` and the runtime use `resolveResponseLanguage(view, navigator.language)`.
6. **Readers moved to the view.** `isLanguageLearningPopupAvailable(view)` is `view.enabled` and `resolveProfile(view, 'edit')` either ok or failing with `credential-missing` / `host-unsupported` (the tools show and the error card explains). `loadConfiguredAssistant` drops its own pre-checks and lets `resolveProfile` produce the `not-configured` error; `aiLanguageToolsRequireInterpreter` and `aiLanguageToolsRequireModel` are removed. `cli-stubs.ts` is unchanged (Phase 7).
7. **Catalog** (`src/ai/catalog.ts`): `import catalog from '../../providers.json'` (enable `resolveJsonModule` in `tsconfig.json`), normalized to `CatalogEntry { id, name, kind, baseUrl, apiKeyUrl?, apiKeyRequired, modelsList?, popularModels }` with `kind` from the `PRESET_KINDS` table, which moves here from `connection-kind.ts` (that module imports it). `apiKeyRequired` is `!== false`. `providers.json` already lists the DeepSeek V4 models, so `DEEPSEEK_V4_MODELS` is dropped with the override. The upstream fetch, `provider_presets` local cache, and the e2e fetch stub are removed.
8. **Settings UI** (`src/settings/ai/`, lazy chunk `settings-ai` replacing `settings-interpreter`). `index.ts` loads the view, builds the panels, and re-renders a panel when `observe` reports its key changed (skipping no-op renders by comparing the serialized panel state). `controller.ts` holds the current view and exposes the mutations, each of which calls one store method and surfaces `AiSettingsStorageError` in the section-level error card. Panels, each built with `document.createElement` into a static container in `settings.html`:
   - `connections.ts`: one card per connection with kind icon, label, host, status badge (**Untested** / **OK** / **Failing** / **Key missing on this device** / **Unsupported in this browser**), **Test**, **Edit**, **Delete**. **Add API provider** opens the catalog picker (plus **Custom**); the connection modal has label, base URL, API key (`type="password"`, a `Show` toggle), **Requires API key**, and an Advanced **Max concurrent requests** number input (`maxConcurrency`, blank = kind default). Saving writes the sync item without the key and the credential to local; editing the base URL or key deletes the status entry. Deleting a connection also deletes its profiles, its credential, its status entry, and any routing entry that pointed at those profiles.
   - `native-cli.ts`: **Add local CLI** (Codex or Grok; one connection per CLI kind, so an existing kind is disabled) creates the connection and a default enabled profile. The existing `wireNativeCliInstallGuide` is re-homed here with its element ids unchanged, shown when `nativeMessaging !== 'none'`. The whole control is hidden when `nativeMessaging === 'none'` (Firefox).
   - `profiles.ts`: profiles grouped under their connection; add, edit (label, model id with a datalist from the catalog's `popularModels` or the last Test listing, effort select for `cli-codex`), enable toggle, duplicate, delete. Order is creation order within a group; drag reorder is removed.
   - `routing.ts`: a table with **Default** on top and one row per task; each row is a `<select>` of enabled profiles (task rows have **Use default**) and shows the resolved profile's connection status badge, which is what the readiness assistant used to answer.
   - `language.ts`, `interpreter.ts` (enable, auto-run, prompt context with the 500 ms debounce), `diagnostics.ts` (5c), `error-card.ts` (decision 11).

   `settings.html` replaces `#interpreter-section` with `#ai-section` and the sidebar item `data-section="ai"` (`aiSettings`, "AI"); `?section=interpreter` is accepted as an alias of `ai` in `settings.ts` so the locale messages that link to it keep working. `SettingsSection` and the three section-name lists gain `ai` and lose `interpreter`. Styles move to `src/styles/ai-settings.scss` (imported from `style.scss`); the settings list rules in `interpreter.scss:266-420` are deleted.
9. **Browser gating.** `detectNativeMessaging()` moves to `src/utils/native-messaging-support.ts` and is shared by `background.ts` and the Settings page. `resolveProfile` already answers `host-unsupported`; the section hides **Add local CLI** and badges synced CLI connections as unsupported where `'none'`. `checkNativeCliHealth` gains a `sendNativeMessage` fallback so Safari's `'message'` mode can run a health check; Safari Test is health plus one-shot exec with no cancel, and the result card says so.
10. **Test** (D3). Client → `{ type: 'test', jobId, connectionId }`; gateway → `{ type: 'test-step', jobId, step: 'listing' | 'probe' | 'structured' | 'health' | 'exec', profileId? }` then `{ type: 'test-result', jobId, result }` or `error`; `cancel` works as for any job. `client.ts` adds `testConnection(connectionId, { signal, onStep })`. Plan per kind, run in `src/ai/test-connection.ts` (pure over injected `fetchImpl` / `executeCli` / `health`):

    | Kind | Free step | Billable step |
    | --- | --- | --- |
    | `openai-compatible` | `GET` models | structured probe unless host is `api.openai.com` |
    | `anthropic` | `GET /v1/models` | none |
    | `ollama` | `GET /api/tags` (`/v1/models` on the `/v1` path) | none |
    | `azure-openai`, `huggingface`, `perplexity` | none | one `max_tokens: 1` completion |
    | `cli-codex` | Host health | one minimal `exec` per enabled profile, with its model and effort |
    | `cli-grok` | Host health | one minimal `exec` |

    Listing URLs are derived in `src/ai/adapters/listing.ts`: the chat path suffix `/chat/completions`, `/v1/messages`, or `/api/chat` is replaced by `/models`, `/v1/models`, or `/api/tags`, keeping the query string; a base URL without a known suffix has no listing and uses the probe. Headers follow `buildApiRequest` for the kind; for `generativelanguage.googleapis.com` the request also sends `x-goog-api-key`. `parseModelList` accepts `data[].id`, `models[].name` (stripping `models/`), and `models[].id`. The listing validates every enabled profile's `model` on the connection; an unlisted model does not fail the connection (the key worked) but is reported per profile and shown as **Model not listed** on the profile row and in the result. The structured probe asks for `{"ok": true}` with `response_format: json_schema`, then `json_object` on a structured rejection, else `none`, with `max_tokens: 16`. The UI shows a cost note above **Test** whenever the plan has a billable step. The `AiTestResult`:

    ```ts
    interface AiTestResult {
      connectionId: string; state: 'ok' | 'failing'; testedAt: number; billable: boolean;
      error?: SerializedAiError;                       // failing only
      models?: { profileId: string; model: string; listed: boolean }[];
      listedModels?: string[];                          // capped at 200 ids
      structuredOutput?: 'json_schema' | 'json_object' | 'none';
      transport?: 'port' | 'message';                   // CLI; 'message' means no cancel
    }
    ```

    **Status** is per device (key validity and CLI installation are), so the gateway persists it to local `ai_connection_status[id] = { state, testedAt, code?, status?, detail?, models? }` when a test finishes, and the Settings page writes `Connection.structuredOutput` (sync) from a result that detected it. Settings may delete status entries (edit, delete, credential change); only the gateway creates them.
11. **structuredOutput fold.** The effective mode in `executeTask` is `status[id].structuredOutput ?? connection.structuredOutput (when not 'unknown') ?? defaultStructuredOutputMode(kind, baseUrl)`. The fallback downgrade writes `status[id].structuredOutput = 'none'` (local, gateway-owned) instead of the `ai_structured_output` cache; a later Test overwrites it. `probeStructuredOutput`, `createStructuredOutputCache`, `createMemoryStructuredOutputCache`, `STRUCTURED_OUTPUT_STORAGE_KEY`, and `deps.structuredOutput` are deleted; `gateway.init()` removes the `ai_structured_output` key once. **Error card:** `src/settings/ai/error-card.ts` renders `describeAiError` with the action mapped to a Settings control (`retry` → run Test again, `copyInstallCommand` → the install guide's copy, `switchProfile` → focus the routing table, `openSettings` → none) and the collapsed technical detail.
12. **Diagnostics** (`src/ai/diagnostics.ts`). `createAiDiagnostics(session?)` with serialized writes and an in-memory fallback, `MAX_ENTRIES = 100` (about 150 bytes each, far below the 10 MB session quota shared with the job store). Entry: `{ at, task: AiTask | 'test', kind, connectionId, durationMs, outcome: 'ok' | 'error' | 'cancelled', code?, status?, structuredMode?, fallback?: true, groups?, retries? }`. Recorded in `gateway.finish` for single calls, once per durable job when it leaves `running` (with group and retry counts, never per group), and per Test. Never content, prompts, keys, or job ids. The Settings panel reads `storage.session` directly (extension pages are trusted contexts), observes `onChanged`, and offers **Clear** and **Copy as JSON**; on a browser without `storage.session` it says diagnostics are unavailable.
13. **Localization and removal.** Every new string is added to `en` and `zh_CN`. Keys that lose their last use (`interpreterExecutionMode*`, `languageLearningReadiness*`, `nativeCliHealth`, `nativeCliHealthDescription`, `apiKeysWarning` if folded, `aiLanguageToolsRequire*`, `providers`, `models` if replaced) are removed from every locale that has them, so `npm run check-strings` stays clean.

## Tasks (each commit green)

### 5a — v2 storage foundation (no behavior change)

1. **Codec, defaults, store** (pure, test-first). `settings.test.ts` with fake areas: decode each key with defaults when absent; corrupt item falls back alone; unknown `kind` dropped; duplicate ids keep the first; Codex options normalized; `encode` round-trips; `assertSyncItemSize` throws at 8,193 bytes and passes at 8,192; a thrown `QUOTA_BYTES_PER_ITEM` error becomes `AiSettingsStorageError('item-too-large')`, `QUOTA_BYTES` → `'total-quota'`, `MAX_WRITE_OPERATIONS_PER_MINUTE` → `'write-rate'`; `observe` fires only for AI keys and names them; `load()` in derived mode equals `deriveAiSettings(v1)` for the `settings-view.test.ts` fixtures and writes nothing.
2. **Migration** (pure, fixtures). `migrate.test.ts`: every legacy shape in decision 4 produces the expected bundle and credentials; `presetId` set from a matching catalog base URL; CLI connection only for the active mode; bootstrap writes five sync keys in one `set` and two local keys in one `set`; a present `ai_connections` is reused and sync is not written; credential import rules (missing local → imported; present → untouched; id in `credentials` → not re-imported; old-build v1 rewrite after migration changes nothing in sync); two-device interleavings; the bundle is byte-identical across two runs over the same input.
3. **Catalog.** `catalog.test.ts`: every `providers.json` entry has a kind, `apiKeyRequired` defaults true, DeepSeek lists the V4 models from the file; `connection-kind.test.ts` still passes using the moved table; `tsconfig.json` gains `resolveJsonModule`; `npx tsc --noEmit --module es2020` and `npm run build:cli` pass.
4. **Readers on the loader.** `native-messaging-support.ts` extracted; gateway deps renamed to `loadAiSettings` (`gateway.test.ts` injects a view built with `deriveAiSettings` from its v1 fixtures; the single-call and durable suites are otherwise unchanged); `interpreter.ts`, `popup.ts`, `language-learning-runtime.ts`, `language-learning-popup.ts`, `language-learning-vocabulary.ts` read the view through `src/utils/ai-settings.ts` in derived mode; `language-learning-runtime.test.ts` and `language-learning-popup.test.ts` inject views; `isLanguageLearningPopupAvailable(view)` cases: disabled, no profile, credential missing still available, host unsupported still available. ## Risks

- **Data loss during bootstrap** is the main risk. Mitigations: the migration is pure with fixtures for every shape; bootstrap writes v2 only when `ai_connections` is absent and never writes v1; v1 stays in sync for the old build; the manual smoke uses a copied real profile.
- **The switch commit (task 9) is large.** Tasks 5–8 land the UI and the retargeted writers as inert or no-op code first so the switch is the HTML swap, the flag, and deletions. If it still exceeds one review, split the deletions into a follow-up commit; the old section can coexist hidden for one commit.
- **Sync quota at a per-key layout** is comfortable (about 30 connections or 40 profiles per item) but the prompt context is user text; the error card and the pre-write size check cover it. The sync write-rate limit (120 per minute) is respected by the 500 ms debounce on text inputs.
- **Two writers of `ai_connections`** are avoided by keeping the gateway's structured-output downgrade in the local status key; the only sync writer is the Settings page (and the one-time bootstrap).
- **Gemini listing auth** on the catalog's `/v1beta/chat/completions` base URL is derived as `/v1beta/models`; if the native listing rejects the Bearer header, `x-goog-api-key` is sent as well. If both fail in a manual check, Gemini falls back to the probe (treat it as a kind without listing) and the plan review notes it.
- **CLI Test duration**: one exec per enabled Codex profile at the CLI timeout; the step messages show which profile is running and cancel works over a port.
- **E2E ordering** around `json_object` → `json_schema` after Test; the mock must accept both, and the assertions are placed in the order given in task 13.
- **`storage.session` on Firefox** needs 115+; the panel handles absence.

## Out of scope

Shared action controller and error card across popup and Reader, and the split of `transcript-language-learning.ts` (Phase 6); removal of v1 `Settings` fields, `loadSettings`'s v1 read, `cli-stubs.ts` AI fields, and `cli-execution.ts` (Phase 7); deletion of v1 storage keys and synced API keys (a later release); separate `openai` / `gemini` / `openrouter` kinds; a `timeoutMs` control; credential encryption or key sync; validating the Host's own model and effort knowledge beyond a minimal exec; Native Messaging installers for browsers other than Chrome.
