# AI Redesign Phases 6 and 7: UI unification and cleanup

Spec: [[2026-10-19-ai-subsystem-redesign-design]]. Previous: [[2026-10-23-ai-redesign-phase-5-settings]]. Branch: `ai-redesign` (HEAD `7edc2d4`, Phases 1–5 landed and reviewed).

**Goal.** Phase 6: every AI entry point (popup Interpreter, popup and side-panel AI edit, Reader bilingual, readings and explain, Settings Test) runs through one action controller with the same run, cancel, retry, progress and stale-result rules, shows errors through one error card driven by `describeAiError`, and the Reader receives `AiError` values end to end instead of the v1 CLI error codes; `src/utils/transcript-language-learning.ts` (1,662 lines) is split into `src/reader/learning/`. Phase 7: the v1 code paths that no longer serve the migration are deleted (`Settings` AI fields and their `loadSettings` reads, the `interpreterEnabled` mirror, the fake settings in `cli-stubs.ts`, the v1 execution-mode concept outside `migrate.ts`, `request-cancellation.ts`), `cli-execution.ts` is deleted, and each default or limit has one home.

Both phases ship as green commits. Each commit passes the focused tests, the full suite with `TZ=America/Los_Angeles`, the type check, and the three builds; the tasks that change chunk contents also run the bundle checks and the Chrome e2e.

## Constraints

- **No new AI features.** Nothing streams into the Reader card or the popup that does not already; cancel and retry are added where the spec already promised them (Interpreter cancel, Phase 2), not elsewhere.
- **v1 storage keys stay.** `interpreter_settings` and `reader_settings.learningResponseLanguage` are not deleted or rewritten. `src/ai/migrate.ts` keeps reading raw v1 sync items; the derived v2 view over v1 (`deriveAiSettings`, the `mode: 'derived'` branch of `readSnapshot`) stays because it is reachable in the bootstrap race and after a failed bootstrap while v1 exists, and is deleted with the keys in the later release. What Phase 7 removes is v1 code that nothing reads any more (the inventory in Decision 10).
- **Explicit cost.** Page-DOM controls that can create model costs keep `event.isTrusted`; the shared controller never starts a run on its own (no auto-retry, no run on construction, no run on reattach), and the card's **Retry**, **Continue remaining** and **Switch and retry** buttons are plain click handlers that the Reader wraps in its trusted-click check. The popup Interpret button keeps accepting the synthetic `interpretBtn.click()` from `handleClipObsidian` (`popup.ts:1366`): it is an extension-owned document, as the docs already state.
- **Background-only network, static imports, no credentials in UI.** Nothing here touches adapters or the gateway's execution path; the gateway change is limited to tagging errors with `task` and `profileId`. `background.js` must stay free of DOM APIs and of `chunks/`.
- **Reader is a content script in the host page's document** (no iframe: the card and selection button are appended to `doc.body`). The shared error card therefore uses only `doc.createElement`, no icons module, no `settings/ai/dom.ts`, and its styles must be imported by both `style.scss` and `reader.scss`.
- **E2E and visual contracts stay.** Selectors asserted by `scripts/extension-e2e.mjs` and `scripts/firefox-e2e.mjs` keep their names: `.language-learning-card` (hidden after restore), `.player-learning-task[aria-busy]`, `.transcript-segment-translation`, `ruby rt`, `.show-bilingual-transcript`, `.show-japanese-readings`, `.ai-connection-test*`, `.ai-status-badge`, `.ai-diagnostics-entry`. `tests/visual/transcript/*.png` (`npm run test:transcript-preview`) screenshot `.player-learning-bilingual` and `.player-learning-readings`, so the controls' classes, order and markup do not change.
- **Bundle budgets** (`scripts/extension-bundle-report.mjs`, raw bytes, measured at HEAD): `background.js` 971,119 / 980,000; `reader-language-learning.js` 158,040 / 160,000; `src_utils_language-learning-runtime_ts.js` 35,601 / 40,000; `popup-language-learning.js` 14,984 / 30,000; `settings-ai.js` 133,379 / 145,000. Decision 12 says what changes.

## Decisions made here

1. **One action controller, pure.** `src/ai/ui/action.ts` exports `createAiAction<T, P = AiActionProgress>(options)`; it has no DOM, storage or browser imports (unit-tested in node), so the popup, the Reader content script and Settings can all import it at the cost of its own bytes.

   ```ts
   type AiActionStatus = 'idle' | 'running' | 'done' | 'cancelled' | 'error';
   interface AiActionProgress { completed: number; total: number; retry?: { delayMs: number; attempt: number } }
   interface AiActionState<P> { status: AiActionStatus; startedAt?: number; progress?: P; error?: AiError }
   type AiActionRun<T, P> = (signal: AbortSignal, report: (progress: P) => void) => Promise<T>;
   interface AiAction<T, P> {
     readonly state: AiActionState<P>;
     start(run: AiActionRun<T, P>): Promise<T | undefined>;   // aborts a previous run first
     retry(): Promise<T | undefined>;                          // re-runs the last `run` with a fresh signal
     cancel(): void;
     dispose(): void;                                          // cancel, then ignore every later settlement
   }
   createAiAction<T, P>({ onChange(state, previous), now? }): AiAction<T, P>
   ```

   Rules, each with a test: a run that settles after a newer `start` (or after `dispose`) changes nothing (this replaces the `explanationRequest` / `activeRequest !== request` counters in the Reader and the `activeRequest === requestController` checks in the popup); every rejection goes through `toAiError`; the settlement is `cancelled` when `signal.aborted` or `error.code === 'cancelled'`, which is what makes message matching (`isRequestCancelled`) unnecessary in UI code; `progress` is kept on the state so the error state still carries the last progress (the card's **Continue remaining (n of m)** label); `onChange` fires on every transition with the previous state so views can clear what they drew. The controller owns no timers: elapsed-time display is the view's job, from `startedAt`.

   The Reader has one controller per transcript (one in-flight transcript request, as today: `startActiveRequest` aborts the previous one) and one for explanations, so an explanation does not cancel a running translation. The popup has one for the Interpreter and one for AI edit. **Settings Test keeps its own state** (`connections.ts:152`, a per-connection map with step progress and a persisted result); it already renders through the error card and gates on a trusted click, and its progress is a `test-step` sequence rather than counts. Converting 729 lines of tested panel code to the controller buys nothing user-visible, so it is out of scope (Out of scope lists it).

2. **One error card, description in, DOM out.** `src/ai/ui/error-card.ts` exports `renderAiErrorCard(container, description: AiErrorDescription, options)` and `clearAiErrorCard(container)`:

   ```ts
   interface AiErrorCardOptions {
     doc?: Document;
     handlers?: Partial<Record<Exclude<AiErrorAction, 'none'>, (event: Event) => void>>;
     /** The profiles for `switchProfile`'s select; without them the action is a plain button. */
     profiles?: { id: string; label: string }[];
     selectedProfileId?: string;
     /** Completed work, which relabels `retry` as Continue remaining (n of m). */
     progress?: { completed: number; total: number };
     onDismiss?: () => void;
     /** An element for the icon slot, e.g. Settings' Lucide placeholder; the Reader passes none. */
     icon?: () => HTMLElement;
   }
   ```

   It renders the markup Settings already has (`.ai-error-card[role=alert]`, `-icon`, `-content`, `-title`, `-body`, `-detail` as a `<details>` with `aiErrorTechnicalDetails`, `-actions`, `-dismiss`) so the Settings e2e and `error-card.test.ts` keep passing. Button rules: the description's `action` is the primary button when a handler for it exists; a `retry` handler is always rendered (primary or secondary) because after fixing the cause elsewhere the user retries here; `continueRemaining` uses the `retry` handler with the `readerContinueRemaining` label when `progress.completed > 0`; `switchProfile` with `profiles` renders a `<select>` plus **Switch and retry** (`readerSwitchAndRetry`), without `profiles` a plain button (Settings focuses the routing table); `openSettings` renders **Open AI settings** (new key `aiErrorActionOpenSettings`); `copyInstallCommand` renders the install guide's copy only where a handler is given (Settings); the popup and Reader map it to `openSettings`, since the guide lives in Settings. Handlers never check `isTrusted` themselves: the Reader wraps each handler.

   Styles move from `src/styles/ai-settings.scss:31-95` to a new partial `src/styles/_ai-error-card.scss`, imported by `src/style.scss` (next to `ai-settings`) and by `src/reader.scss` (after `styles/reader/transcripts`), using only variables both documents define (`--background-modifier-error`, `--background-modifier-error-border`, `--text-error`, `--text-muted`, `--font-ui-small`, `--font-ui-smaller`, `--radius-m`); the `corner-shape` line stays in `ai-settings.scss` scoped to the Settings page.

   `src/settings/ai/error-card.ts` keeps `describeSettingsError` (storage and bootstrap errors are Settings-only) and `renderErrorCard`, which now calls the shared renderer with the Settings handlers and `createIcon`. Its tests are unchanged.

   `openSettings` is one background message for every context: the existing `{ action: 'openOptionsPage' }` handler (`background.ts:734`) gains an optional `section`, and opens `settings.html?section=ai` through `tabs.create` when a section is given (`openOptionsPage()` cannot take a query). Content scripts can send runtime messages, so the Reader card offers it too.

3. **`AiError` end to end; the runtime stops wrapping.** `AiErrorOptions`, `AiError`, `SerializedAiError`, `serializeAiError` and `deserializeAiError` gain optional `task?: AiTask` and `profileId?: string`; the gateway sets both on every error it emits for a single call or a durable job (it resolves the profile, so it knows them). `describeAiError` is unchanged. In `language-learning-runtime.ts`, `LanguageLearningRequestError`, `LEGACY_ERROR_CODES`, `NATIVE_HOST_ERROR_CODES`, `RequestContext.mode`, the `InterpreterExecutionMode` import and `toLanguageLearningError` are deleted; `requireProfile` throws `new AiError('not-configured', { reason, task })` and the catch blocks rethrow `withTask(toAiError(error), task, profileId)` only when the gateway did not set them (the pre-check path). The one special case, a CLI timeout after the runner already split groups, stays in the runtime: `toTranscriptJobError` returns `new AiError('timeout', { ...fields, retryable: true, detail })` with a new option `recovery: 'continue-remaining'`, and `describeAiError` renders `readerTranscriptTranslationBatchFailed` as the body when that field is set (the key is already localized). `toAiError` keeps `'LanguageLearningRequestError'` in `NATIVE_ERROR_NAMES` until Phase 7 removes it.

   The Reader card consumes `AiError` directly: title from `describeAiError(error).title`, body, collapsed detail (`aiErrorTechnicalDetails`), **Switch and retry** for `error.task` (the readings flow's translate step reports `task: 'translate'`, as today), preselecting `error.profileId`. The `readerCli*` keys (8), `readerTechnicalDetails`, `interpreterExecutionMode` and `interpreterExecutionModeApi` lose their last use in this phase and are removed from every locale (Decision 14). `interpreterExecutionModeCodex` / `Grok` stay: `connectionDisplayName` names unlabeled CLI connections with them.

4. **Cancellation is `cancelled` for the UI now, everywhere in Phase 7.** Phase 6 UI code recognizes cancellation only through the controller (Decision 1). Phase 7 deletes `src/utils/request-cancellation.ts`: `throwIfRequestAborted` and `raceWithRequestCancellation` move to `src/ai/abort.ts` (pure) and throw `new AiError('cancelled')`; `native-cli-service.ts` and `language-learning.ts` import them from there; `toAiError` drops the `'RequestCancelledError'` and `'LanguageLearningRequestError'` name matches and keeps `'AbortError'` (a `fetch` abort). ## Risks

- **Reader chunk budget.** Phase 6 lands over 160,000 before Phase 7 recovers it; Task 5 raises the budget on purpose and Task 14 re-measures. If `job-limits.ts` does not recover the expected 15–20 KB (webpack may already tree-shake the runner), the final budget stays near 175,000, which is still the measured size plus headroom, not a regression in behavior.
- **The split is the largest diff.** Task 5 does the mechanical move first and the behavior change second inside one commit; if review wants two commits, the mechanical move (re-exports, moved tests, no behavior change) can land alone, green, with the controller adoption after it.
- **Error-shape change across the runtime boundary.** The runtime's 43 tests and the Reader's error cases are rewritten to `AiError`; the e2e covers only the hidden card, so the manual smoke's error cases are the real check. `task` and `profileId` are optional on the wire, so an older background during an update cannot break a newer page.
- **Interpreter state is polled by CSS class** (`waitForInterpreter`); adding `cancelled` must also be handled there, or a cancelled autoRun would make a Clip wait forever. Task 4's test covers it.
- **`{{"prompt"}}` default.** Dropping the placeholder stays the default for `api.ts` consumers (current behavior); only the CLI with `--execution-mode` and the popup keep it. If a downstream consumer of `dist/api.mjs` relied on the placeholder surviving, it did not: it was always dropped.
- **Shared `.mjs` constants.** Webpack bundles `native-host/cli-invocation.mjs` into the extension; it has no imports and is already bundled through `cli-execution.ts` today, so no new build behavior. The `.d.mts` must declare the arrays `as const` or `CodexReasoningEffort` widens to `string`; the type check catches it.
- **Locale removals** touch every locale file; `check-strings` and a grep for each removed key before deletion keep a used key from being removed.
